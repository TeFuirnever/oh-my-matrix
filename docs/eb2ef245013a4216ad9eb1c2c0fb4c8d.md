## 摘要

本报告系统化梳理 MatrixAssistant 在 OpenClaw 内核下执行长任务时遇到的三大痛点（任务没完全执行、任务结果偏移、任务执行不完整），并从三个层面给出完整的理论与工程分析：

1. **行业范式层**：Loop Engineering、/goal、TRAE SOLO、Codex Agent Loop 的横向对比
2. **学术根基层**：ReAct → Reflexion → LATS 谱系、Agentic Overconfidence 量化证据、PRM/ORM 奖励模型、多智能体协作的真相
3. **落地路径层**：基于学术证据优先级排序的改进方案、风险推演、对助手落地的思考

**核心结论**：当前长任务执行失败的根因是「判题不分离 + 无可验证停止条件 + 单轨迹局部最优」。学术证据表明，让执行模型自评会产生 38–55pp 的过自信偏差，这是工程上必须消除的系统性风险。改进的最小可行路径是「独立 Evaluator + 对抗式 prompt + Ownership 消除 + Reflection 记忆」四重保障。

## 1. 问题定义与现状诊断

### 1.1 三大痛点

MatrixAssistant 基于 OpenClaw 内核执行长任务时，反复出现以下问题：

| 痛点 | 表现 | 根因（学术视角） |
|------|------|------------------|
| 任务没完全执行 | Agent 跑几轮就停，需手动续行 | 缺少跨轮续跑机制，无 Goal-Based Loop 原语 |
| 任务结果偏移 | 输出与用户意图渐行渐远 | 无独立 Evaluator，模型自评产生 38–55pp 过自信偏差 |
| 任务执行不完整 | 模型说完成但实际未完成 | 无可验证停止条件，"模型完成 ≠ 任务完成" |

### 1.2 当前已有基础

基于 [docs/core/autopilot/design.md](./design.md) 和 [electron/utils/todo-executor.ts](../../../electron/utils/todo-executor.ts)：

- **Autopilot 设计已对标 Claude Code ultracode**，有 `before_agent_finalize` 同 turn revise（G1）
- **Evidence Gate** 在 `complete()` 前必须通过（G3），但当前是**规则级**，缺**模型级**
- **单一权限模式** full_yolo + 安全边界（network 自动、rm/credential/unknown 拦截）
- **TodoExecutor + Gateway Cron** 已有调度基础
- **Skills 系统、MCP Connectors** 已就位
- **memory/ 目录** 已有 dreaming 机制可做长期记忆载体
- **state/ 目录** 已有 `cancel-signal-state.json` 模式可复用

### 1.3 关键缺口

- ❌ 无独立 Evaluator 模型（判题分离缺失）
- ❌ 无 Goal-Based Loop 原语（完成条件驱动）
- ❌ 评估器无文件系统隔离保护
- ❌ 无硬上限预算控制
- ❌ 跨轮续跑的状态恢复机制薄弱
- ❌ 无 Reflection 式失败记忆
- ❌ 无 LATS 式多分支探索（单轨迹局部最优）

## 2. 行业范式对比：Loop Engineering 谱系

### 2.1 四层范式演进

| 阶段 | 年份 | 关注点 | 一句话 | AI 自主时长 |
|------|------|--------|--------|-------------|
| Prompt Engineering | 2023 | 怎么写好一次提示 | 把话说清楚 | 单次问答 |
| Context Engineering | 2024 | 怎么管理上下文窗口 | 把对的信息喂进去 | 数十步连续 |
| Harness Engineering | 2025 | 怎么搭单次运行脚手架 | 给 Agent 一套趁手工具 | 连续数小时 |
| **Loop Engineering** | 2026 | 怎么让脚手架自己定时跑 | 把"做好一次"变成"自动做很多次" | 连续数天/并行上百 |

### 2.2 Loop Engineering 的核心主张

> "Loop engineering is replacing yourself as the person who prompts the agent. You design the system that does it instead." —— Addy Osmani (Google, 2026-06)

**核心转变**：把人从「循环里的操作员」挪到「循环外的设计者」。

### 2.3 五块积木 + 一个记忆

| 积木 | 功能 | 通俗比喻 |
|------|------|----------|
| Automations | 定时/事件触发，任务发现 + triage | 系统的心跳 |
| Worktrees | 多 Agent 并行隔离，避免文件冲突 | 每人一间办公室 |
| Skills | 项目知识固化到 SKILL.md，跨会话复用 | 桌面的工作手册 |
| Connectors | 基于 MCP 接入 GitHub/Slack/DB | 通向真实世界的门 |
| Sub-agents | Maker-Checker 分离，避免自校验偏差 | 专业分工团队 |
| Memory | 跨会话状态持久化 | 长期记忆 |

### 2.4 Loop 的四步核心循环

```
Act（行动）→ Observe（观察）→ Reason（推理）→ Repeat（重复）
```

关键区别在最后一步：传统方式是人判断"继续还是停"，Loop Engineering 是**系统自动判断**。

### 2.5 两大必要条件

1. **触发器（Trigger）**：什么启动 Loop？定时任务？PR 事件？CI 失败？
2. **可验证的目标（Verifiable Goal）**：怎么判断"完成了"？测试全绿？TypeCheck 通过？

> "If your task has no verifiable goal — you did not build a loop. You built a very confident token furnace." —— Addy Osmani

### 2.6 四大隐性风险

1. **验证债务**：代码看起来能跑，细微错误悄悄合进主分支
2. **理解腐化**：AI 写太快，人对代码库理解脱节
3. **认知投降**：审查几十轮后不再质疑，变成橡皮图章
4. **Token 失控**：死循环一晚上烧掉一周预算

## 3. 产品实践对比：/goal、Loop、TRAE SOLO、Codex Agent Loop

### 3.1 Claude Code 的四种 Loop 原语

| 类型 | 触发方式 | 适用场景 | 命令示例 |
|------|----------|----------|----------|
| Turn-Based | 用户发消息 | 临时修改、探索 | 默认模式 |
| **Goal-Based** | 完成条件触发 | bug 修复、性能优化 | `/goal npm test exits 0, stop after 5 tries` |
| Time-Based | 定时触发 | 监控 CI/CD、PR review | `/loop 5m` |
| Proactive | 云端事件触发 | issue triage、大规模迁移 | `/schedule every hour: ...` |

### 3.2 /goal 的判题分离设计

**核心机制**：判题分离（Judgment-Execution Separation）
- 主模型（Opus/Sonnet）干活：读代码、改文件、跑测试
- 评估模型（默认 Haiku）判卷：每轮结束后**只读对话记录**判断条件是否达成
- **关键约束**：评估器**不碰文件系统、不跑命令**——防止 Agent 篡改证据通过检查
- 未达到 → 自动开下一轮，把 reason 喂给主模型作为下一轮指导
- 达到 → 清除 goal，记录达成

**完成条件四要素**：
1. 可量化的终点
2. 明确的验证方式
3. 约束条件（保持不变的部分）
4. 硬上限（`or stop after 20 turns`）

### 3.3 TRAE SOLO 的反思机制

TRAE（字节跳动 AI Native IDE）的核心循环基于 ReAct，但增加关键创新：

**三大 Skill 构成闭环**：
- Execution（RunTerminalCommand）：AI 直接操作终端
- Modification（Edit）：AI 写文件系统，生成 Diff
- Perception（Codebase Search/RAG）：全局索引代码仓库

**SOLO 模式**：双智能体分工
- SOLO Builder：从 0 到 1 创建原型
- SOLO Coder：复杂项目迭代/重构/Bug 修复
- Subagent 体系：自动分配任务给不同子智能体

**Trae-Agent 开源核心**（2025-07）：
- `execute_task()` 是核心循环
- 流程：向 LLM 发消息 → 解析工具调用 → 执行工具 → **对结果进行反思** → 将结果 + 反思喂回 LLM → 重复直到完成或达到 max_steps
- **Lakeview**：为 Agent 步骤生成简短精确摘要，用于上下文压缩

### 3.4 Codex Agent Loop 的三段式闭环

OpenAI 2026-01-27 工程博客《Unrolling the Codex Agent Loop》：

**Agent Loop 定义**：
```
accept user input → craft a prompt → ask model for response
→ act on tool calls → append tool outputs → repeat until final assistant message
```

**Turn vs Round 区分**：一次 Turn（用户发一条消息到 Agent 回复）中，可能包含多轮 model 推理 + tool call 循环。

**GPT-5.3-Codex 四层结构**：

| 层 | 职责 |
|----|------|
| L1 Harness | 上下文组装：系统指令、AGENTS.md、打开的文件、历史 |
| L2 模型 | GPT-5.3-Codex：规划、选工具、生成 patch/命令 |
| L3 工具层 | shell、apply_patch、MCP、web_search… |
| L4 循环控制 | 审批、沙箱、stop hooks、compaction |

**三段式生产级闭环**（Cookbook 2026-05-11）：

| 阶段 | 做什么 | **不做什么**（关键约束） |
|------|--------|--------------------------|
| Review | 读制品，输出结构化 findings | **不改文件** |
| Repair | 按 findings + 上轮 Validate 反馈做最小改动 | **不宣称已通过** |
| Validate | 跑真实检查（测试、规则 judge） | **不把主观"看起来对"当 pass** |

### 3.5 Codex-maxxing 长程任务五要素

1. **Durable thread**：给长期任务固定会话，维护上下文/旧决策/待办/用户反馈
2. **Memory**：不只依赖聊天记录，把项目状态、决策、开放事项写进可 diff、可复用的文件
3. **Steering**：用户可中途补充 prompt（"先不要接短信登录""等预览部署完再继续"）
4. **Thread automation**：定时任务（等部署、看 review、查工单）
5. **Goals**：目标必须量化（页面/接口/测试/异常分别达到什么结果）

### 3.6 横向对比总表

| 维度 | Loop Engineering | /goal | TRAE SOLO | Codex Agent Loop | **MatrixAssistant 现状** |
|------|------------------|-------|-----------|------------------|--------------------------|
| 循环范式 | 范式（上层） | Goal-Based 原语 | ReAct + 反思 | Review-Repair-Validate | Autopilot before_finalize |
| 判题分离 | Sub-agents | Evaluator 模型 | 反思机制 | 三段式阶段隔离 | Evidence Gate（规则级，缺模型级） |
| 状态持久化 | Memory 积木 | --resume | 轨迹记录 | Durable thread + docs/* | state/ + memory/ 已就位 |
| 中途注入 | - | - | - | Steering | ❌ 缺失 |
| 上下文压缩 | - | - | Lakeview | Prompt Caching + Compaction | compact/ 已有，缺 step-summary |
| 权限边界 | - | - | 多模式+高危检测 | 沙箱+审批 | full_yolo + 安全边界 |
| 长程模板 | - | - | - | Codex-maxxing 五要素 | ❌ 缺 Durable thread |
| 子 Agent 分工 | Sub-agents | - | Subagent 体系 | Subagents | agent-team/ 可扩展 |
| 模型/端侧分工 | - | 双模型 | - | 四层结构 | OpenClaw 内核 + Electron |

## 4. 学术根基：从 ReAct 到 LATS 的演进逻辑

ReAct、Reflexion、LATS 不是孤立的"模式"，而是 Princeton 姚顺雨博士论文《Language Agents: From Next-Token Prediction to Digital Automation》系统化的语言智能体方法论。这条演进线有严格的学术逻辑。

### 4.1 ReAct 的形式化贡献（ICLR 2023）

ReAct 的真正学术价值不在"边思考边行动"，而在于**动作空间的形式化扩展**：

$$\mathcal{A} = \mathcal{A}_{\text{external}} \cup \mathcal{A}_{\text{language}}$$

- $\mathcal{A}_{\text{external}}$：外部动作（搜索、点击、API 调用），会改变环境状态
- $\mathcal{A}_{\text{language}}$：语言空间动作（Thought/推理轨迹），**不影响外部环境，只更新内部上下文**

**关键洞见**：「思考也是一种行动」。这对应认知科学中的"认知操作"（cognitive operation）。ReAct 把 LLM 的动作空间从离散工具扩展到"工具+语言"，让模型像选择"向左走"一样自主选择"思考下一步"。

**ReAct 的致命缺陷**（学术界公认）：**线性贪婪解码 + 错误传播**。CoT 一旦第一步错，后续推理无论多严密都基于错误前提。这被称为 *Error Propagation*。

### 4.2 Reflexion 的 RL 视角（NeurIPS 2023）

Reflexion 不是简单"失败后反思"，而是把**强化学习的反馈思想**引入语言 Agent：

- 标准 RL 设置：奖励模型给二元奖励，动作空间遵循 ReAct
- **关键创新**：引入启发式函数 $h(\tau)$ 判断轨迹是否低效或含幻觉
- 低效规划 = 长时间未成功的轨迹；幻觉 = 与观察不一致的断言
- 失败后由 Critic LLM 生成文字反思，存入 Memory，指导下次重试

**Reflexion 的学术局限**：仍是**单轨迹（Single Trajectory）的深度优先试错**。若初始决策方向全局次优，会在局部修修补补，陷入局部最优。

### 4.3 LATS 的 MCTS 范式（NeurIPS 2023）

LATS（Language Agent Tree Search）把 AlphaGo 的 MCTS 移植到语言 Agent，针对 Reflexion 的局部最优问题。其六步循环有严格数学基础：

**UCT 选择公式**：
$$UCT_i = V_i + c \cdot \sqrt{\frac{\ln N}{n_i}}$$

- $V_i$：节点平均累积价值（Exploitation）
- $N$：父节点访问总数；$n_i$：当前节点访问次数
- 第二项：探索未知的潜力（Exploration）
- $c$：探索常数

**LATS 区别于传统 MCTS 的关键**：在 AlphaGo 中评估靠自我对弈到终局或 Value Network；LATS 引入 **LLM Critic** 做前端评估（pre-action evaluation），并加入第六步 **Reflect**（失败后反思）。

**学术意义**：LATS 是 ReAct（执行）+ Reflexion（反思）+ MCTS（全局寻优）的统一框架，把语言 Agent 从"一条道走到黑"提升到"在状态-动作树上全局搜索"。

### 4.4 谱系对 MatrixAssistant 的启示

当前 OpenClaw 内核的 Autopilot 本质是**单轨迹 ReAct + 规则级 Evidence Gate**，缺：
- Reflexion 式的失败反思记忆（指导下一轮重试）
- LATS 式的多分支探索（避免局部最优）

**最低成本落地**：在 [todo-executor.ts](../../../electron/utils/todo-executor.ts) 的循环中，失败轮次不直接重试，而是先让模型生成 Reflection 存入 memory/，作为下一轮 prompt 的额外上下文。

## 5. 学术铁证：自我评估的不可靠性

「让模型自己判分」的不可靠性不是经验之谈，是有严格量化证据的。

### 5.1 Agentic Overconfidence 的量化证据（ICML 2026）

Kaddour 等人在 100 个 SWE-Bench-Pro 任务上的实验给出**惊人数据**：

| 模型 | 真实成功率 | 模型自评成功率 | 过自信差距 |
|------|-----------|---------------|-----------|
| GPT-5.2-Codex | 35% | 73% | **+38pp** |
| Gemini-3-Pro | 22% | 77% | +55pp |
| Claude Opus 4.5 | 27% | 72% | +45pp |

**三个反直觉发现**：

1. **Pervasive Overconfidence（普遍过自信）**：所有前沿模型都系统性高估自己，差距巨大
2. **More Context, Uncalibrated Doubt（更多上下文，未校准的怀疑）**：Mid-execution 阶段模型信心下降，但这个怀疑**没有信息量**——成功和失败案例同样出现怀疑
3. **Adversarial Framing Helps（对抗式提问有效）**：把"验证正确性"改写为"找 bug"可降低过自信 15pp，校准效果最好

### 5.2 Ownership Bias 与 Chat Template（arXiv 2606.03437）

Sanz-Guerrero 等人发现 chat template 加剧过自信，机制是 **Ownership Bias**：

- 模型对自己生成的答案比相同答案（由用户提供）多给最高 **26%** 的置信度
- 推理时策略：把模型答案**改写为 user input** 再做置信度评估，可降低过自信 26%

### 5.3 Capability Self-Assessment 的缺失（arXiv 2606.00251）

Yang 等人定义 **CSA（Capability Self-Assessment）**：模型判断"这个问题是否在我能力边界内"的能力。实证发现：

- 现代模型**系统性缺乏 CSA**：跨模型家族和规模，都倾向于回答超出能力边界的问题
- SFT 严重损害 CSA，而 RL（RLVR）能教会 CSA 且保留原有能力
- CSA 是可迁移的模型特质，不是特定于训练分布的

### 5.4 对 MatrixAssistant 的硬启示

这三篇论文直接证伪了"让 OpenClaw 执行模型自己判 Evidence Gate"的可行性。**学术上的必然结论**：

1. **执行模型和评估模型必须分离**——这不是工程审美，是数学必然。同一模型自评会产生 38–55pp 的过自信偏差
2. **评估器必须用对抗式 prompt**——"find bugs" 而非 "verify correctness"，这是 ICML 2026 量化验证的最佳校准策略
3. **评估时应消除 ownership bias**——把执行模型的输出改写为"用户提供的待评估方案"再喂给评估器，而非作为"模型自己的输出"
4. **CSA 缺失意味着模型不会主动说"我做不了"**——必须由端侧 Agent 强制注入能力边界检查，不能依赖模型自报

这四条直接对应 [docs/core/autopilot/design.md](./design.md) 的 Evidence Gate 设计，要求从"规则级"升级到"独立模型 + 对抗式 prompt + ownership 消除"三重保障。

## 6. 奖励模型：PRM 与 ORM 的本质分野

### 6.1 ORM vs PRM

OpenAI《Let's Verify Step by Step》定义了两种奖励模型：

| 类型 | 反馈粒度 | 局限 |
|------|---------|------|
| **ORM（Outcome Reward Model）** | 只看最终答案对错（0/1） | 稀疏奖励；"歪打正着"（过程错但答案对）得高分 |
| **PRM（Process Reward Model）** | 对每一步打分 | 数据标注成本高；"局部流畅但结论错"会被高分 |

**经典反例**：
```
步骤1：3×4=11（错）
步骤2：7×2=15（错）
步骤3：11+15=26（基于前两步正确）
步骤4：答案26（恰好正确）
```
ORM 给正面反馈；PRM 正确指出步骤1、2 错误。

### 6.2 PRM 的工程化挑战与 PROGRS 方案（arXiv 2604.02341, 2026）

Rezaei 等人指出 PRM 的三个失败模式：

1. **Miscalibration**：PRM 分数与最终正确性不一致
2. **Locally fluent failure**：奖励局部流畅但全局错误的推理
3. **Reward hacking**：作为绝对奖励时会诱导模型钻空子

**PROGRS 的核心创新——Outcome-Conditioned Centering**：

- 不把 PRM 分数当绝对目标，而是作为**结果分组内的相对偏好**
- 在每个 prompt 组内，把错误轨迹的 PRM 分数平移到均值为零
- 移除系统性偏差，保留有信息的排序
- 配合 frozen quantile-regression PRM + 多尺度 coherence evaluator

**实验结果**：MATH-500 上 Pass@1 从 69.7% 提升到 74.9%；AMC-2023 从 52.0% 到 59.0%。

### 6.3 PAV：Google DeepMind 的过程优势验证器（arXiv 2410.08146）

Setlur 等人提出更本质的过程奖励定义：

- **每步的过程奖励 = 采取该步前后，生成正确答案概率的变化**
- 这对应 RL 中的**逐步骤优势（per-step advantage）**
- 关键：用与基础策略**不同的证明策略（prover policy）**来度量

**反直觉发现**：弱证明器策略可以显著改善强基础策略。原因是优势度量了"探索"对最终答案的贡献，而 Q 值只"利用"已知好状态。

**实验**：测试时搜索准确率比 ORM 提升 8%，计算效率提升 1.5-5 倍；在线 RL 样本效率提升 5-6 倍。

### 6.4 对 MatrixAssistant 的启示

当前 Autopilot 的 Evidence Gate 是 **ORM 式**——只看最终结果（测试是否通过、文件是否改对）。学术建议：

1. **引入 PRM 式的逐步骤评估**：不只是看"任务完成了吗"，而是评估每个 tool call 步骤是否合理
2. **采用 PROGRS 的 outcome-conditioned centering**：避免执行模型"局部流畅但全局错误"的步骤被高分
3. **PAV 的"优势"视角**：评估每步时问"这步让任务更接近完成了吗"，而非"这步本身漂亮吗"

**落地建议**：在 [compact-executor.ts](../../../src/lib/compact-executor.ts) 的每轮 tool call 后，调用独立 Evaluator 做步骤级评估，存入 trajectory，最终轮间判断时综合 PRM 分数 + ORM 结果。

## 7. 多智能体协作的真相

### 7.1 "Debate Only When Necessary"（arXiv 2504.05047, 2025）

DOWN 框架的核心发现：多智能体 debate 并非总是有益，反而有三大问题：

1. **计算开销**：迭代交互导致 6 倍 agent calls 增长
2. **错误传播**：冗余 debate 生成错误，被其他 agent 传播放大
3. **MAD（Multi-Agent Debate）框架悖论**：agent calls 比单 agent 多，准确率反而下降

**DOWN 的方案**：基于初始响应的 confidence score，**只在必要时才触发 debate**。confidence-guided debate 同时缓解错误传播和选择性吸纳可靠响应。

### 7.2 "Diversity Collapse 与 Manufactured Overconfidence"（TMLR 2026 在审）

这篇直接质疑多智能体 debate 的核心承诺：

- **"When Consensus Is Not Correctness"**：共识不等于正确
- **Diversity Collapse**：debate 过程中 agent 观点趋同，多样性坍缩
- **Manufactured Overconfidence**：多 agent 达成共识后，集体置信度被人为制造出来，但与正确性无关

### 7.3 Knight-Knave-Spy 控制实验（arXiv 2511.07784, 2025）

Wu 等人用可验证 ground truth 的逻辑谜题做受控研究，发现：

- **内在推理强度和群体多样性是 debate 成功的主导驱动**
- 结构参数（顺序、置信度可见性）收益有限
- **多数压力压制独立纠正**：少数正确 agent 会被多数错误 agent 压制
- **有效团队推翻错误共识**：真正有效的团队能翻转错误共识，而非平均

### 7.4 对 MatrixAssistant 多 Agent 设计的警示

这些论文对 [packages/agent-team/](../../../packages/agent-team) 的设计是直接警示：

1. **不要盲目上多 Agent**——多 Agent debate 不是"越多越好"，错误的 agent 会传播错误，多余的 debate 反而降低准确率
2. **必须引入 confidence-gated 机制**——只在主 agent 置信度低时才扇出 debate，对应 DOWN 框架
3. **警惕 Diversity Collapse**——多 agent 要保持认知多样性，不能让它们快速趋同。DiMo 框架的"四种不同推理范式 agent"是正解
4. **防止多数暴政**——Reviewer agent 数量不能多，且要给"少数派报告"留通道，否则正确但少数的观点会被压制

## 8. 长程任务的基准真相

### 8.1 SWE-Bench Verified 的饱和与 SWE-Bench Pro 的残酷

| 基准 | 任务特征 | 顶级模型 Pass@1 |
|------|---------|----------------|
| SWE-Bench Verified | 161 个任务仅需 1-2 行修改 | 70%+（饱和） |
| **SWE-Bench Pro** | 平均 107.4 行/4.1 文件，至少 10 行 | **23.3%（GPT-5）** |

商业集（专有代码库）更惨：Claude Opus 4.1 仅 17.8%，GPT-5 仅 14.9%。

### 8.2 故障模式分析（LLM-as-judge 用 GPT-5）

| 模型 | 主要失败模式 |
|------|-------------|
| Claude Opus 4.1 | 错误解决方案（35.9%）+ 语法错误（24.2%） |
| GPT-5 | 错误解决方案（51.7%），工具使用率 97.6% |
| Claude Sonnet 4 | 上下文溢出（35.6%） |
| Qwen-3 32B | 工具使用错误（42.0%） |

**关键洞见**：前沿模型失败在**语义理解和算法正确性**，而非执行；小模型失败在**上下文管理和工具使用**。这是不同层次的瓶颈。

### 8.3 长程多轮 RL 训练的突破（arXiv 2508.03501, 2025）

Golubev 等人证明 RL 可训练长上下文多轮 SWE Agent：

- 方法：RFT（rejection fine-tuning）+ 同步 RL pipeline（DAPO 算法）
- 应用到 Qwen2.5-72B-Instruct，SWE-bench Verified Pass@1 从 11% → 39%
- 关键：**执行反馈做 RL 奖励**，环境对每个 action 给非平凡观察

### 8.4 对 MatrixAssistant 的基准校准

1. **真实长程任务成功率只有 15–25%**——MatrixAssistant 用 OpenClaw 内核做长任务，预期成功率不应高于此区间，必须设计成"默认失败、循环救场"
2. **故障模式决定改进方向**——若用前沿模型，瓶颈在语义理解（需要更强的 Plan/Review 阶段）；若用小模型，瓶颈在上下文管理（需要更强的 compaction 和工具调用保障）
3. **RL + 执行反馈是已验证的提升路径**——但这是模型训练层的事，端侧 Agent 能做的是"模拟 RL 信号"：每轮收集执行反馈，作为下一轮 prompt 的明确奖惩信号

## 9. 模型层与端侧 Agent 的协同分工

「模型完成 ≠ 任务完成」的根因在于模型与端侧 Agent 职责边界模糊。综合 ACP（Agent Client Protocol）标准和各厂商实践，清晰的分工如下。

### 9.1 三角色模型（ACP 标准化）

| 角色 | 职责 | 落地位置 |
|------|------|----------|
| **Client（IDE/端侧）** | 承载用户交互、提供 cwd 和本地环境、暴露文件系统/终端、决定哪些 tool call 需用户确认 | 端侧（MatrixAssistant 主进程 + 渲染器） |
| **Agent（harness）** | 处理用户提示、调模型、维护会话状态、报告计划/输出/工具进度 | OpenClaw 内核（plugin orchestrator） |
| **MCP Server** | 连接外部工具/数据源 | packages/gateway + MCP connectors |

### 9.2 模型层负责什么

| 能力 | 说明 |
|------|------|
| **推理与生成** | 规划、选工具、生成 patch/命令、生成回复 |
| **意图识别** | 解析用户自然语言，决定下一步 |
| **反思** | 对工具结果做二次评估（Trae-Agent 的反思机制） |
| **判断** | 评估器模型判断 goal 是否达成（/goal 的 Haiku 角色） |

### 9.3 端侧 Agent（Harness）负责什么

| 能力 | 说明 |
|------|------|
| **上下文组装** | System/Developer/Assistant/User 角色拼装、tools 广告、environment 注入 |
| **工具执行** | 在受控沙箱执行 tool call，捕获 stdout/stderr |
| **状态管理** | 会话历史、checkpoint、resume |
| **上下文压缩** | 调用专门 API 压缩旧对话，管理 token 预算 |
| **权限控制** | 哪些命令自动执行、哪些需用户确认、高危命令拦截 |
| **循环控制** | stop hooks、max_steps、熔断 |
| **判题分离** | 独立 Evaluator 调用，不让执行模型自判 |
| **持久化** | 把状态/决策/待办写入可 diff 的文件（docs/、memory/） |

### 9.4 关键协同原则

1. **模型只负责"想"，端侧负责"做和判"**——模型不碰文件系统、不跑命令，端侧 Agent 执行
2. **判题分离必须跨模型实例**——执行模型和评估模型不能是同一个，否则自我说服（/goal 用 Haiku 判 Opus 的输出）
3. **Steering 必须支持中途注入**——长任务跑一半用户可补充约束，不丢上下文（Codex Steering）
4. **Memory 必须落磁盘**——跨会话状态不能放上下文窗口，要可 diff、可复用（AGENTS.md + docs/* 模式）
5. **端侧是信任边界**——权限、沙箱、高危命令拦截都在端侧，模型层不承担安全责任

## 10. 改进方案与优先级排序

### 10.1 理论最小可行升级（按学术证据强度排序）

| 优先级 | 学术依据 | 改进项 | 预期效果 | 对应痛点 |
|--------|---------|--------|---------|---------|
| **P0** | ICML 2026 Agentic Overconfidence | 独立 Evaluator 模型 + 对抗式 prompt（"find bugs"） | 消除 38–55pp 过自信偏差 | 任务结果偏移 |
| **P0** | arXiv 2606.03437 Ownership Bias | 评估时把执行输出改写为 user input | 降低 26% ownership bias | 任务结果偏移 |
| **P1** | NeurIPS 2023 Reflexion | 失败轮次生成 Reflection 存入 memory/ | 避免相同错误重复 | 任务执行不完整 |
| **P1** | arXiv 2508.03501 RL + 执行反馈 | 每轮收集 pass/fail 信号作为下一轮明确奖惩 | 模拟 RL 信号 | 任务没完全执行 |
| **P1** | /goal 判题分离 | Goal-Based Loop 原语 + 完成条件四要素 | 跨轮自动续跑 | 任务没完全执行 |
| **P2** | OpenAI PRM / PROGRS | 逐步骤评估（不只看最终结果） | 捕捉"局部流畅但全局错误" | 任务结果偏移 |
| **P2** | Codex 三段式 | Review → Repair → Validate 阶段隔离 | 阶段级判题分离 | 任务结果偏移 |
| **P2** | arXiv 2504.05047 DOWN | Confidence-gated 多 Agent 扇出 | 避免冗余 debate 的错误传播 | 任务执行不完整 |
| **P3** | NeurIPS 2023 LATS | 多分支探索 + UCT 选择 | 避免局部最优 | 任务执行不完整 |
| **P3** | TMLR Diversity Collapse | 保持 Reviewer agent 认知多样性 | 防止共识坍缩为虚假置信 | 任务结果偏移 |
| **P3** | Codex-maxxing | Durable thread + Steering 中途注入 | 长程任务不丢上下文 | 任务没完全执行 |

### 10.2 判题分离三重保障（学术最小可信设计）

综合 ICML 2026 + arXiv 2606.03437 + arXiv 2606.00251，独立 Evaluator 必须满足：

1. **模型实例分离**：执行模型和评估模型不能是同一模型实例（ICML 2026 量化证据）
2. **Prompt 对抗化**：评估器用"find bugs"而非"verify correctness"（降低 15pp 过自信）
3. **Ownership 消除**：把执行输出改写为"用户提供的待评估方案"再喂评估器（降低 26pp bias）
4. **能力边界检查（CSA）**：评估器先判断"这个任务是否在执行模型能力边界内"，再判断是否完成（arXiv 2606.00251）

**这四条是学术界给出的最小可信判题分离设计，缺一不可。**

### 10.3 三段式 Review-Repair-Validate 闭环

直接对标 Codex Cookbook，在 [Autopilot orchestrator](./design.md) 中把循环显式拆三阶段：

```
┌─────────┐     ┌─────────┐     ┌──────────┐
│ Review  │────▶│ Repair  │────▶│ Validate │
│ (只读)  │     │ (最小改) │     │ (真实跑) │
└─────────┘     └─────────┘     └──────────┘
     ▲                                 │
     └─────────── 失败反馈 ◀───────────┘
```

| 阶段 | 做什么 | **不做什么** |
|------|--------|--------------|
| Review | 读制品，输出结构化 findings（JSON schema） | **不改文件** |
| Repair | 按 findings + 上轮 Validate 反馈做最小改动 | **不宣称已通过** |
| Validate | 跑真实检查（build/test/lint） | **不把"看起来对"当 pass** |

### 10.4 Goal-Based Loop 原语设计

在 Autopilot 之上增加 `/goal` 等价命令：

**用户输入**：
- 完成条件（≤4000 字符）
- 硬上限（`stop after N turns` / `max tokens M`）

**每轮流程**：
1. 主模型执行
2. 独立 Evaluator 评估条件（只读对话记录，不碰文件）
3. 未满足 → reason 作为下一轮指导喂回主模型
4. 满足 → 清除 goal，记录达成

**状态指示器**：运行时长、轮数、token 消耗、最近 reason

**完成条件四要素**（写入 [AGENTS.md](../../../AGENTS.md) 指南）：
1. 可量化的终点（`npm test 退出码 0`）
2. 明确的验证方式（`CHANGELOG.md 包含每个 PR 条目`）
3. 约束（`不修改其他测试文件`）
4. 硬上限（`或超过 20 轮后停止`）

### 10.5 Steering 中途注入能力

对标 Codex Steering，在 [todo-executor.ts](../../../electron/utils/todo-executor.ts) 的循环中支持：

- 用户在 Agent 跑到第 N 轮时补充约束（"先不要改这个文件""等部署完再继续"）
- 注入不丢上下文，作为下一轮 prompt 的 user 角色增量
- 任务从"一次性指令"进化为"可边做边调整的任务队列"

### 10.6 跨轮状态持久化与恢复

**对标 Loop Engineering 的 Memory 积木**：

- 每轮结束后将 `{round, goal, lastReason, attempts, tokenSpent, filesChanged}` 写入 [state/](../../../state)（已有 `cancel-signal-state.json` 模式）
- 应用崩溃/重启后可恢复 goal 上下文
- 复用现有 [memory/](../../../memory) 目录的 dreaming 机制做长期记忆

### 10.7 预算护栏与熔断

**对标四大风险中的 Token 失控**：

- 每轮记录 token 消耗，累计超过预算阈值触发熔断
- 检测连续 N 轮无进展（相同错误重复）自动停止
- 复用 [rate-limiter.ts](../../../electron/utils/rate-limiter.ts) 扩展为 budget-limiter
- 熔断后通知用户，附带最近 reason 链供人工介入

### 10.8 渐进式落地顺序（对标 Claude Code 官方建议）

不要一上来搞全自动。建议顺序：

1. 先写 verification skill（验证流程固化到 SKILL.md）
2. 再在任务有明确验证指标时用 goal-based loop
3. 最后才考虑 proactive loop（云端定时）

## 12. 对助手落地的思考

### 12.1 MatrixAssistant 的独特定位

MatrixAssistant 不是纯 CLI Agent，也不是纯 IDE，而是 **Electron 桌面应用 + OpenClaw 内核 + 多角色 + 多窗口** 的组合体。这决定了：

1. **端侧能力天然强**：主进程可做权限、沙箱、持久化、多窗口协作
2. **角色系统已就位**：[electron/utils/role-manager.ts](../../../electron/utils/role-manager.ts) 已支持多角色，天然适合 Sub-agent 分工
3. **Gateway + Bastion 已就位**：[packages/gateway/](../../../packages/gateway) + [packages/bastion/](../../../packages/bastion) 提供安全控制层
4. **Skills + MCP 已就位**：[resources/skills/](../../../resources/skills) + MCP connectors 提供工具层
5. **memory + dreaming 已就位**：[memory/](../../../memory) 目录的 dreaming 机制可做长期记忆

**这意味着落地改进时，不需要从零造基础设施，而是把学术发现映射到现有架构。**

### 12.2 落地路径的三个阶段

#### 阶段一：判题分离（P0，最快见效）

**目标**：解决"任务结果偏移"

**动作**：
1. 在 OpenClaw plugin 的 `before_agent_finalize` hook 引入独立 Evaluator
2. Evaluator 用更便宜但够聪明的模型（对标 Sonnet 5 / Haiku 角色）
3. **关键约束**：Evaluator 只读对话记录，不碰文件系统、不跑命令
4. Evaluator 用对抗式 prompt："find bugs in this solution"而非"verify correctness"
5. 把执行模型输出改写为"用户提供的待评估方案"再喂 Evaluator（消除 ownership bias）
6. Evaluator 输出结构化 `{satisfied, reason, nextHint, capabilityInBounds}`
7. 未满足 → reason 作为下一轮指导喂回主模型；满足 → 放行 complete()

**对应 Autopilot G3「Evidence Gate」**：把 Evidence Gate 从规则校验升级为模型判卷。

#### 阶段二：Goal-Based Loop + Reflection（P1）

**目标**：解决"任务没完全执行"和"任务执行不完整"

**动作**：
1. 实现 `/goal` 等价命令（完成条件 + 硬上限）
2. 失败轮次生成 Reflection 存入 [memory/](../../../memory)
3. 每轮收集 pass/fail 信号作为下一轮明确奖惩（模拟 RL 信号）
4. 跨轮状态持久化到 [state/](../../../state)，支持 resume
5. Steering 中途注入（用户可补充约束）

#### 阶段三：三段式闭环 + 多分支探索（P2/P3）

**目标**：对标 Codex 三段式 + LATS 多分支，提升长任务成功率

**动作**：
1. 循环显式拆 Review → Repair → Validate 三阶段
2. 引入 PRM 式逐步骤评估
3. Confidence-gated 触发 Reviewer agent 扇出（DOWN 框架）
4. 保持 Reviewer 认知多样性（DiMo 式四种推理范式）
5. LATS 式多分支探索 + UCT 选择（可选，成本高）

### 12.3 与现有 Autopilot 设计的对齐

本报告不取代 [docs/core/autopilot/design.md](./design.md)，而是为其提供**理论升级路径**：

| Autopilot 现有设计 | 本报告建议升级 |
|--------------------|----------------|
| G1 before_agent_finalize 同 turn revise | 保留，增加跨轮续跑 |
| G3 Evidence Gate（规则级） | 升级为独立 Evaluator + 对抗式 prompt + ownership 消除 |
| 单一权限模式 full_yolo | 保留，Evaluator 阶段加文件系统隔离 |
| 单一写入原则 orchestrator | 保留，三段式阶段在 orchestrator 内拆分 |
| 增量扩展（OpenClaw plugin 内） | 保留，不引入独立 daemon |

### 12.4 对助手产品的哲学思考

**长任务执行的本质矛盾**：模型能力在涨，但任务复杂度涨得更快。SWE-Bench Pro 的 23% 告诉我们，**长任务默认就是会失败的**。

**这要求助手产品的设计哲学从"努力让它成功"转为"假设它会失败，设计循环救场"**：

1. **默认失败、循环救场**：每个长任务都预设会失败，设计循环 + Reflection + 多分支来救场
2. **人机协作而非全自动**：关键决策点强制人工 review，避免认知投降
3. **可观测性优先**：每轮的 reason、token、进度必须可见，否则用户就是橡皮图章
4. **边界诚实**：模型不会主动说"我做不了"（CSA 缺失），端侧必须强制能力边界检查，超界时主动建议人工介入或切换更强模型
5. **成本可控**：预算硬上限 + 熔断是前提，否则 token 失控会毁掉产品信任

## 13. 未来推演

### 13.1 短期（3–6 个月）

- **判题分离成为标配**：所有主流 Agent 产品都会引入独立 Evaluator，类似 /goal 的 Haiku 判 Opus 模式
- **Goal-Based Loop 原语普及**：完成条件驱动的跨轮续跑成为 Agent 标配
- **Reflection 记忆标准化**：失败反思存入持久 memory 成为共识
- **ACP 协议初步收敛**：Agent ↔ IDE 通信标准化，MatrixAssistant 应对齐最小面

### 13.2 中期（6–12 个月）

- **模型层 RL 训练成熟**：长程多轮 RL 训练（如 arXiv 2508.03501）让模型本身具备更强的长任务能力，端侧 Agent 的救场负担减轻
- **PRM 工程化**：逐步骤评估从学术走向产品，Evaluator 不只判最终结果，还判每个步骤
- **多 Agent 协作成熟**：confidence-gated debate + 认知多样性保持成为多 Agent 标准模式
- **Proactive Loop 落地**：云端定时事件触发的主动式 Loop 成为差异化能力

### 13.3 长期（1–2 年）

- **L1–L5 自主分级收敛**：DeepSeek 论文提出的 L1（自动补全）到 L5（完全自主研究）分级成为行业标准，MatrixAssistant 应明确目标定位在 L3–L4
- **模型训练与端侧 Agent 协同**：模型层 RL 训练 + 端侧判题分离形成正反馈，模型在端侧反馈数据上持续微调
- **多模态长任务**：不只是代码，还包括浏览器、桌面应用、文档处理的端到端长任务
- **认知投降的工程对策**：强制人工 review、可解释性增强、对抗式审查成为合规要求

### 13.4 对 MatrixAssistant 的战略推演

**机会窗口**：
- 学术界已给出清晰的理论根基，但工程化落地仍在早期
- 国内市场对长任务执行能力的工程化落地尚处空白
- MatrixAssistant 的端侧能力（Electron + 多角色 + Gateway + Bastion）天然适合做判题分离和多 Agent 协作

**战略建议**：
1. **短期**：快速落地 P0（判题分离），形成差异化卖点
2. **中期**：对齐 ACP 协议，开放 Agent 生态，不被 OpenClaw 锁定
3. **长期**：在端侧反馈数据上做模型微调，形成数据飞轮

**风险警示**：
- 不要盲目追求 L5 完全自主，L3–L4 是务实目标
- 不要忽视认知投降风险，人机协作是长期答案
- 不要让 token 成本失控，预算护栏是产品生存前提
